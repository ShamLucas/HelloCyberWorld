## 1) Un secret retiré du fichier n'est pas un secret retiré du dépôt

En supprimant `hermes_api_server_key` de `group_vars/hp_envy.yml`, on modifie
l'état courant du fichier — mais git ne remplace jamais un commit, il en
ajoute un nouveau. Le commit `bad6203` qui a introduit la clé existe encore
dans l'historique, avec le blob complet, et il est déjà répliqué sur
`origin/docker` (donc public sur GitHub) au moment où on l'a découvert.

Conséquences pratiques :
- Toute personne ayant cloné le dépôt avant la correction a la clé, même si
  on la retire ensuite.
- `git log -p -- chemin/du/fichier` ou simplement l'historique GitHub suffit
  à la retrouver.
- La seule vraie remédiation est soit de **réécrire l'historique**
  (`git filter-repo`, BFG Repo-Cleaner — disruptif, à coordonner si d'autres
  personnes ont cloné), soit de considérer la clé comme grillée et de la
  **faire tourner (rotation)** côté service si celui-ci existe encore.

Décision prise cette séance : le service Hermes étant supprimé, la clé n'a
plus d'usage réel — on laisse l'historique tel quel plutôt que de réécrire.

## 2) Docker protège ses volumes tant qu'un conteneur les référence

Ordre utilisé pour retirer Hermes et Open WebUI du serveur :

```
docker compose down       # arrête et retire le conteneur
docker volume rm ...      # supprime le volume nommé
rm -rf .../services/...   # supprime le dossier de la stack
rm nginx vhost + reload   # retire la route HTTP
certbot delete --cert-name ...
```

Pourquoi cet ordre : Docker **refuse** `docker volume rm` tant qu'un
conteneur (même arrêté, pas seulement en cours d'exécution) référence encore
ce volume. La commande échoue avec une erreur explicite
(`volume is in use - [container_id]`) plutôt que de laisser un conteneur
avec un point de montage cassé. C'est une protection intégrée, pas un piège :
inverser l'ordre bloque proprement, ça ne corrompt rien.

Là où un problème réel peut apparaître, c'est si le **conteneur tourne
encore** et qu'on supprime le volume par un autre biais (bind mount plutôt
que volume nommé, ou volume détruit hors Docker) : dans ce cas le processus
à l'intérieur du conteneur perd son fichier ouvert ou son point de montage,
et plante ou renvoie des erreurs applicatives.

## 3) 500 vs 502 : où est la panne ?

Utile pour diagnostiquer un service derrière Nginx (Portainer, Open WebUI,
Hermes, ou un futur projet) :

- **500 Internal Server Error** : le service backend a répondu, mais il a
  planté en traitant la requête. Le problème est *dans* l'application.
- **502 Bad Gateway** : Nginx agit en reverse proxy et n'arrive pas à
  obtenir de réponse valide du backend (conteneur arrêté, port fermé,
  connexion refusée). Le problème est *entre* Nginx et le service.
- **504 Gateway Timeout** : Nginx a joint le backend mais n'a pas eu de
  réponse dans le délai imparti.

Distinguer les deux oriente le diagnostic : 500 → regarder les logs du
conteneur ; 502 → vérifier que le conteneur tourne et que le port/réseau
Docker est correct.

## 4) Séparer le socle (Ansible) de la plateforme (déploiement de projets)

Le brainstorm de cette séance a fait émerger une distinction structurante
pour la suite du projet :

- **Ansible = socle, idempotent, rejoué rarement.** Il sait construire un
  serveur Debian avec Docker, Nginx, Certbot, Portainer, et la forge git
  elle-même. Il ne connaît **aucun projet** en particulier.
- **Couche plateforme = à construire, non triviale.** C'est elle qui doit
  savoir transformer *un dépôt poussé* en service déployé : build de
  l'image, sous-domaine, certificat, éventuellement identité utilisateur
  (JWT) pour un espace tenant. Ansible ne fait pas ce travail — c'est un
  rôle conceptuellement différent (orchestration applicative, pas
  provisioning d'hôte).

Cette séparation est directement inspirée de YunoHost, avec un angle
"forge de développement" plutôt que "app store" : chaque projet est un
dépôt, chaque dépôt peut devenir un sous-domaine.

Décision explicite : l'arbitrage "construire cette couche soi-même vs
adopter un outil existant (Coolify, CapRover, Dokku...)" est repoussé à une
discussion au niveau Virtual2dBrain (contrainte de temps : recherche
d'emploi + formation ML/IA en octobre).
