# 12. Vhost HTTPS conditionnel : Ansible propriétaire de nginx, Certbot des certificats

> Séances des 29 et 30/09/2026, branche `certbot-certonly`. Première étape :
> le vhost racine (rôle `nginx`), validé sur la VM. Restent le rôle `certbot`
> en `certonly`, puis les vhosts de `docker-platform` et `markdown-site`.
> Précise le diagnostic du `doc/11` §4.

## 1) Le diagnostic, précisé : un « ping-pong »

Le play HP Envy enchaîne `docker-platform`, `nginx`, `markdown-site`, puis
`certbot`. À chaque exécution :

1. les templates `nginx` et `docker-platform` réécrivent les vhosts **en HTTP
   seul** → `changed` ;
2. la tâche `certbot install --nginx`, **sans `creates:`**, tourne à chaque
   fois et **réinjecte le HTTPS** dans ces mêmes fichiers → `changed` ;
3. en fin de play, les handlers rechargent nginx, HTTPS compris.

L'état final était bon, donc tout semblait fonctionner. Mais le play n'était
jamais idempotent, et le `--check` affichait des diffs à chaque passage.
Depuis que `markdown-site` échoue (placé avant `certbot`), l'étape 2 n'est
plus atteinte et les handlers ne tournent plus : la config sans HTTPS reste
écrite sur le disque, sans rechargement.

## 2) La cible : un seul propriétaire par fichier

Un certificat, ce sont deux actions distinctes :

- **l'obtenir** : Certbot demande à Let's Encrypt, qui délivre
  `fullchain.pem` (certificat + chaîne intermédiaire) et `privkey.pem` (clé
  privée) dans `/etc/letsencrypt/live/<domaine>/` ;
- **l'utiliser** : la config nginx (`listen 443 ssl`, `ssl_certificate`,
  `ssl_certificate_key`).

Choix retenu : **Certbot en `certonly`** ne fait plus que la première ;
**chaque rôle qui déclare un vhost** porte la seconde dans son template.
Critère de réussite : un play rejoué donne `changed=0`, et un `--check`
redevient lisible.

Deux pièges connus :

- **l'œuf et la poule** : sur un serveur neuf, un vhost qui pointe vers un
  certificat absent empêche nginx de démarrer, donc de servir le challenge
  HTTP-01, donc d'obtenir le certificat. Le bloc HTTPS n'est écrit **que si
  le certificat existe** ;
- **le renouvellement** : en mode `--nginx`, Certbot rechargeait nginx
  lui-même. En `certonly`, il faut un *deploy hook* qui le fait, sinon nginx
  sert l'ancien certificat jusqu'à son expiration.

## 3) Le code (rôle `nginx`)

`roles/nginx/tasks/main.yml`, juste avant `Copier la configuration Nginx` :

```yaml
- name: Verifier si le certificat existe
  stat:
    path: /etc/letsencrypt/live/{{ nginx_server_name }}/fullchain.pem
  register: nginx_cert
```

`stat` prend en entrée **ce qu'il faut regarder** (`path`) et renvoie **ce
qu'il a trouvé** ; `register` range toute la réponse, dont
`nginx_cert.stat.exists`. En `--check`, `stat` s'exécute **pour de vrai**
(lecture seule) : le template choisit donc la bonne branche et le diff
affiché est exact.

`roles/nginx/templates/nginx.conf.j2` :

```nginx
server {
{% if nginx_cert.stat.exists %}
    listen 443 ssl;
    ssl_certificate     /etc/letsencrypt/live/{{ nginx_server_name }}/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/{{ nginx_server_name }}/privkey.pem;
{% else %}
    listen 80;
{% endif %}
    server_name {{ nginx_server_name }};
    root /var/www/html;
    index index.html index.htm;
    location / {
        try_files $uri $uri/ =404;
    }
}
{% if nginx_cert.stat.exists %}
server {
    listen 80;
    server_name {{ nginx_server_name }};
    return 301 https://$host$request_uri;
}
{% endif %}
```

| | Bloc 1 | Bloc 2 |
|---|---|---|
| Sans certificat | port 80, sert le site | absent |
| Avec certificat | port 443, sert le site | port 80, redirige vers https |

Le contenu du site n'existe qu'une fois. Le second `if` garantit un seul bloc
par port : sans lui, deux blocs sur le port 80 avec le même `server_name`.

Les lignes `include /etc/letsencrypt/options-ssl-nginx.conf` et `ssl_dhparam`
des vhosts réécrits par Certbot ne sont **pas** reprises : elles viennent du
plugin nginx de Certbot, abandonné ici.

## 4) Tester sur la VM

**Chaque morceau là où il peut être testé fidèlement.** Let's Encrypt ne peut
pas joindre la VM (adresse privée, pas de port 80 entrant) : pointer un nom DNS
vers elle ne suffirait pas. La VM teste donc **la logique du template** avec un
certificat auto-signé (nginx ne distingue pas) ; **Certbot** se testera sur le
serveur réel avec `certbot certonly --dry-run` (staging, rien d'écrit).

Le rôle `common` échoue actuellement sur la VM (voir §6). Pour ne jouer que le
rôle `nginx` :

```bash
ansible-playbook playbook.yml --limit dev --check --diff \
  --start-at-task "Collecter la liste des services"
```

**a. Sans certificat** : le diff ne montre qu'un retour à la ligne final ;
`curl -i http://192.168.56.10` → `200 OK`.

**b. Avec certificat.** Dans la VM :

```bash
sudo mkdir -p /etc/letsencrypt/live/dev.hellocyberworld.com
sudo openssl req -x509 -nodes -newkey rsa:2048 -days 30 -keyout /etc/letsencrypt/live/dev.hellocyberworld.com/privkey.pem -out /etc/letsencrypt/live/dev.hellocyberworld.com/fullchain.pem -subj "/CN=dev.hellocyberworld.com"
```

(`-x509` : un certificat directement ; `-nodes` : clé sans mot de passe, sinon
nginx en demanderait un au démarrage.) Prédire le diff **avant** le check —
`listen 80` remplacé par `listen 443 ssl` et les deux lignes de certificat,
bloc de redirection ajouté — puis vérifier et appliquer :

```bash
curl -i  http://192.168.56.10    # 301 Moved Permanently, Location: https://...
curl -i  https://192.168.56.10   # refus : self signed certificate
curl -ik https://192.168.56.10   # 200 OK
```

Le refus sans `-k` est une preuve : nginx sert bien le certificat auto-signé.

**c. Idempotence** : même commande rejouée → `changed=0`, aucun handler.

Le faux certificat doit être **supprimé avant de tester le rôle `certbot`** :
Certbot refuse un dossier `live/` qu'il n'a pas créé.

## 5) Certificats et sous-domaines

- Un certificat couvre la **liste exacte** des noms qu'il contient :
  `hellocyberworld.com` ne couvre pas `portainer.hellocyberworld.com`.
- Options : un certificat par nom (situation actuelle), un certificat à
  plusieurs noms (`-d a -d b`), ou un joker `*.hellocyberworld.com`, qui ne
  couvre pas le domaine nu et exige le challenge **DNS-01** (accès à l'API du
  registrar, donc un secret à gérer).
- Un certificat Let's Encrypt **se refabrique** (gratuit, 90 jours, renouvelé
  automatiquement) : inutile de le sauvegarder. Attention à la limite de 5
  certificats identiques par semaine : les tests passent par le staging.

## 6) Pièges rencontrés

- **`common` cassé sur machine neuve** : Claude Code exige Node ≥ 22, les
  dépôts fournissent Node 12 (Ubuntu 22.04), 18 (24.04) ou 20 (Debian 13).
  Un hôte en échec est **retiré des plays suivants** : le play Dev ne tourne
  plus du tout.
- **La VM n'est pas celle du `VagrantFile`** : il annonce `ubuntu/noble64`,
  elle tourne en 22.04 (créée avant le changement, jamais recréée).
- **Arguments collés** : `- out` au lieu de `-out` → `req: Use -help for
  summary` (« je ne comprends pas tes arguments »).
- **Lire la première ligne de l'erreur** : `git git commit ...` →
  `'git' is not a git command`.
- **Ligne de commande sur plusieurs lignes** : terminer chaque ligne par `\`,
  dernier caractère, sans espace après.
- **Git, trois zones** : répertoire de travail → `git add` → index →
  `git commit`. `git commit --amend` reprend **l'index** et remplace le
  dernier commit ; `--no-edit` garde le message. Seulement sur un commit non
  poussé.
- **tmux `mouse on` dans le terminal VS Code** : la souris part à tmux. Pour
  une sélection native, activer
  `terminal.integrated.macOptionClickForcesSelection` et sélectionner avec
  `⌥ Option`. Coller depuis le presse-papier du Mac : `Cmd+V` (le clic droit
  ouvre le menu de tmux, qui colle son propre tampon).
