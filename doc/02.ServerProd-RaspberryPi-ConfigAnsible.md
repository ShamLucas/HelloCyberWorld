# 🥝 Déploiement sur Raspberry Pi avec Ansible

Ici nous allons décrit comment préparer et déploier les services sur un Raspberry Pi en production, en réutilisant les rôles Ansible développés pour l’environnement de test.

---

## 1️⃣ Préparer l’inventaire Ansible pour le Raspberry Pi

On ajoute une section dédiée à la production dans le fichier d’inventaire :

```ini
[prod]
raspberrypi ansible_host=IP_DU_PI ansible_user=pi ansible_ssh_private_key_file=~/.ssh/id_rsa
```
Remplacer `IP_DU_PI` par l’adresse IP réelle du Raspberry Pi.

---

## 2️⃣ Adapter le playbook pour la production

On peut utiliser le même playbook que pour la VM, ou créer un playbook spécifique à la prod :

```yaml
- hosts: prod
  become: yes
  roles:
    - common
    - nginx
    # Ajouter ici d’autres rôles nécessaires en production
```

---

## 3️⃣ Préparer le Raspberry Pi

- Installer Raspberry Pi OS ou Ubuntu Server sur le Pi.
- Configurer l’accès SSH : on génère une clé SSH et on copie la clé publique sur le Pi.
  
```bash
ssh-copy-id pi@IP_DU_PI
```

- Vérifier que le Pi est accessible :

```bash
ssh pi@IP_DU_PI
```

- sur le pi, il faut configurer pour qu'il se lance sur le ssd et non la carte SD

---

## 4️⃣ Configuration du SSD du boitier DeskPi Pro V2

Comme le DeskPi Pro V2 permet d'utiliser un disque SSD, on va directement le configurer dans Ansible. Ainsi le jour où le Pi a un souci, le disque SSD tombe, etc., nous pourrons facilement tout réinstaller sur un nouvel environnement de production. 

Le DeskPi Pro V2 utilise un adaptateur SATA–USB pour connecter le SSD.
Par défaut, le bootloader EEPROM du Pi démarre sur la carte SD.

Le rôle `pi-setup` va automatiquement :

1. **Détecter** si le SSD est vierge ou contient déjà un système
2. **Cloner** le système de la carte SD vers le SSD si nécessaire (partition, formatage, rsync)
3. **Configurer** le bootloader EEPROM pour démarrer sur le SSD en priorité

⚠️ **Important** : Ce rôle ne s'exécute **que** sur un Raspberry Pi. Il détecte automatiquement le type de machine et s'arrête si ce n'est pas un Pi, donc il peut être inclus dans le playbook principal sans risque pour la VM Vagrant.

### 🧩 1. Créer le rôle

Dans le dossier ansible, lance :

```bash
cd ansible
ansible-galaxy init roles/pi-setup
```

### 📁 2. Structure de base

```
roles/
  pi-setup/
    tasks/
      main.yml
    templates/
    handlers/
    vars/
    defaults/
```

### ⚙️ 3. Contenu du fichier roles/pi-setup/tasks/main.yml

```yaml
---
# tasks file for pi-setup
# Ce rôle ne doit s'exécuter que sur un Raspberry Pi

- name: Vérifier que nous sommes bien sur un Raspberry Pi
  stat:
    path: /proc/device-tree/model
  register: device_tree

- name: Lire le modèle du device
  command: cat /proc/device-tree/model
  register: device_model
  changed_when: false
  when: device_tree.stat.exists

- name: Arrêter si ce n'est pas un Raspberry Pi
  fail:
    msg: "Ce rôle ne peut s'exécuter que sur un Raspberry Pi"
  when: not device_tree.stat.exists or 'Raspberry Pi' not in device_model.stdout

- name: S'assurer que le paquet rpi-eeprom est installé
  apt:
    name: rpi-eeprom
    state: present
    update_cache: yes

- name: Mettre à jour le firmware EEPROM (bootloader)
  command: rpi-eeprom-update -a
  become: yes
  register: eeprom_update
  changed_when: "'*** INSTALLING' in eeprom_update.stdout"

# Étape 1 : Détecter si le SSD est vierge ou déjà configuré
- name: Détecter le périphérique SSD (généralement /dev/sda)
  stat:
    path: /dev/sda
  register: ssd_device

- name: Vérifier si le SSD a des partitions
  shell: lsblk /dev/sda -o NAME,MOUNTPOINT | grep -q "/"
  register: ssd_has_root
  failed_when: false
  changed_when: false
  when: ssd_device.stat.exists

- name: Afficher l'état du SSD
  debug:
    msg: >
      {% if not ssd_device.stat.exists %}
      Aucun SSD détecté sur /dev/sda
      {% elif ssd_has_root.rc == 0 %}
      Le SSD contient déjà un système (monté sur /)
      {% else %}
      Le SSD est présent mais semble vierge ou non monté sur /
      {% endif %}

# Étape 2 : Cloner la SD vers le SSD si nécessaire
- name: Installer rsync si nécessaire
  apt:
    name: rsync
    state: present
  when: ssd_device.stat.exists and ssd_has_root.rc != 0

- name: Créer une partition sur le SSD si vierge
  shell: |
    # Créer une table de partition
    parted /dev/sda --script mklabel msdos
    # Créer une partition primaire qui prend tout l'espace
    parted /dev/sda --script mkpart primary ext4 0% 100%
    # Formater en ext4
    mkfs.ext4 -F /dev/sda1
  register: ssd_partitioned
  when: ssd_device.stat.exists and ssd_has_root.rc != 0

- name: Monter temporairement le SSD pour le clonage
  mount:
    path: /mnt/ssd
    src: /dev/sda1
    fstype: ext4
    state: mounted
  when: ssd_device.stat.exists and ssd_has_root.rc != 0

- name: Cloner le système de la SD vers le SSD
  shell: |
    rsync -axHAWX --info=progress2 / /mnt/ssd/ \
      --exclude=/mnt/* \
      --exclude=/proc/* \
      --exclude=/sys/* \
      --exclude=/dev/* \
      --exclude=/tmp/* \
      --exclude=/run/* \
      --exclude=/lost+found
  when: ssd_device.stat.exists and ssd_has_root.rc != 0
  async: 1800  # 30 minutes max
  poll: 10

- name: Mettre à jour /etc/fstab sur le SSD
  lineinfile:
    path: /mnt/ssd/etc/fstab
    regexp: '^(PARTUUID|/dev/mmcblk0p2)\s+/\s+'
    line: '/dev/sda1  /  ext4  defaults,noatime  0  1'
  when: ssd_device.stat.exists and ssd_has_root.rc != 0

- name: Mettre à jour cmdline.txt pour pointer vers le SSD
  replace:
    path: /boot/cmdline.txt
    regexp: 'root=[^\s]+'
    replace: 'root=/dev/sda1'
  when: ssd_device.stat.exists and ssd_has_root.rc != 0

- name: Démonter le SSD temporaire
  mount:
    path: /mnt/ssd
    state: unmounted
  when: ssd_device.stat.exists and ssd_has_root.rc != 0

# Étape 3 : Configurer le boot order dans l'EEPROM
- name: Vérifier la configuration actuelle du bootloader
  command: rpi-eeprom-config
  register: eeprom_config
  changed_when: false

- name: Afficher la configuration actuelle du bootloader
  debug:
    var: eeprom_config.stdout_lines

- name: Modifier l'ordre de boot pour démarrer sur SSD (USB) en priorité
  become: yes
  shell: |
    set -e
    TMP=$(mktemp)
    rpi-eeprom-config > "$TMP"
    if ! grep -q "^BOOT_ORDER=0xf41" "$TMP"; then
      sed -i 's/^BOOT_ORDER=.*/BOOT_ORDER=0xf41/' "$TMP" || echo "BOOT_ORDER=0xf41" >> "$TMP"
      rpi-eeprom-config --apply "$TMP"
      echo "Boot order updated to SSD first (0xf41)"
    else
      echo "Boot order already configured (0xf41)"
    fi
    rm -f "$TMP"
  register: boot_order
  changed_when: "'updated' in boot_order.stdout"

- name: Vérification du périphérique racine actuel
  command: mount | grep " / "
  register: root_device
  changed_when: false

- name: Afficher le périphérique racine actuel
  debug:
    msg: "Système actuellement démarré sur {{ root_device.stdout }}"

- name: Message final
  debug:
    msg: >
      {% if ssd_has_root.rc == 0 %}
      ✅ Le système tourne déjà sur le SSD !
      {% elif ssd_device.stat.exists %}
      ⚠️  Le SSD a été configuré et le boot order modifié. REDÉMARRER le Pi pour booter sur le SSD.
      {% else %}
      ❌ Aucun SSD détecté. Vérifier la connexion du SSD au DeskPi Pro V2.
      {% endif %}
```

### 🧠 4. Ajout dans playbook.yml

Ajoute le rôle au playbook principal :

```yaml
---
- hosts: raspberrypi
  become: yes
  roles:
    - pi-setup

```

Et dans inventory.ini :

``ìni
[raspberrypi]
192.168.1.190 ansible_user=pi ansible_password=raspberry
```

### 🧪 5. Exécution

Lance le playbook sur le Raspberry Pi :

```bash
ansible-playbook -i ansible/inventory.ini ansible/playbook.yml --limit raspberrypi
```

👉 Ce rôle :

Vérifie qu'on est bien sur un Raspberry Pi

Met à jour le bootloader EEPROM,

Clone le système de la carte SD vers le SSD,

Configure le boot sur SSD (BOOT_ORDER=0xf41),

Propose de redémarrer si la copie et la configuration s'est bien passé,

Affiche le tout dans la console.

## 🔐 Let's Encrypt / Certbot (optionnel)

Pour générer automatiquement un certificat TLS pour le Pi, le rôle `pi-setup` peut installer `certbot` et demander un certificat Let's Encrypt en utilisant la validation HTTP (webroot).

Prérequis :
- Le rôle `nginx` doit être exécuté avant `pi-setup` (ou le webroot configuré et servi) pour que la validation HTTP fonctionne.
- Le domaine (`certbot_domain`) doit pointer vers l'IP du Pi (DNS public) ou être accessible depuis l'Internet si vous utilisez Let's Encrypt production.

Exemple de fichier `group_vars/pi.yml` (à créer dans le repo) :

```yaml
# Activer la génération du certificat
certbot_enable: true
# Nom de domaine public pointant sur le Pi
certbot_domain: pi.example.com
# Email pour l'enregistrement Let's Encrypt
certbot_email: admin@example.com
# Webroot utilisé par nginx (doit être servi)
certbot_webroot: /var/www/html
```

Utilisation :
- Vérifier que `nginx` est configuré et sert `{{ certbot_webroot }}`.
- Déployer le playbook :

```bash
ansible-playbook -i ansible/inventory.ini ansible/playbook.yml --limit raspberrypi
```

Le rôle `pi-setup` installera `certbot` et obtiendra le certificat si `certbot_enable` est `true` et `certbot_domain` est renseigné.


## 7️⃣ Redémarrage

Si le SSD était vierge et a été cloné, **redémarre le Pi** pour qu'il boote sur le SSD :

```bash
ssh pi@192.168.1.100
sudo reboot
mount | grep " / "
# Devrait afficher : /dev/sda1 on / type ext4 ...
```
